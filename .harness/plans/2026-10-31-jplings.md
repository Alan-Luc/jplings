# jplings — Personalized Japanese Learning System

Status: ready
Updated: 2026-10-31

## Goal and context

Turn one learner's fragmented, exposure-derived Japanese into coherent, retained, independently usable everyday conversational ability before a trip in ~April 2027 (≈6 months). Rustlings' loop is the model: **Learn → Exercise → Feedback → Demonstrate → Progress → Revisit later**, with an emphasis on doing over recognizing.

The learner is a beginner in practical proficiency with strong receptive intuition: reads hiragana, some katakana/kanji; understands familiar spoken expressions; can assemble basic but particle/conjugation-inconsistent sentences; has compositional number knowledge (diagnosed correct structure at 38,750); weak on godan/ichidan conjugation, tense/te-form production, particle functions, もう/まだ distinctions, and indirect pragmatic meaning. Speaking and listening are the top priorities; reading (manga, signs) matters; handwriting is out of scope.

The speech infrastructure direction is already decided by prior research (handoff §8A) and is not re-opened: Whisper via whisper.cpp with Vulkan GPU on the RX 9060 XT, Kokoro 82M via ONNX Runtime on CPU, independent Docker containers on the NixOS host. Remaining speech work is validation and benchmarking on the real machine, not technology selection.

Source of record for learner requirements: `docs/references/handoff.md` (the full project handoff, verbatim).

Repository state: `/home/alan/dev/jplings` was an empty directory; a setup-only git init + "Initialize repository" commit (README, .gitignore) was created on 2026-10-31 to give the harness a HEAD. No application code exists.

## Requirements and acceptance

This section is the concise product requirements document.

### Functional

- **R1 — Core learning loop.** A session is a sequence of small steps (learn, practice, listen, speak, converse, review). Sessions of varying length (handoff §2: weekdays 30–60 min, weekends 1–2 h; shorter partial sessions allowed) advance the curriculum without breaking progression; state persists and resumes cleanly mid-unit.
- **R2 — Declarative content.** Curriculum content (units, lessons, exercises, rubrics, explanations, accepted answers) lives in data files, separate from the execution engine. Adding or editing a lesson never requires recompiling the engine.
- **R3 — Exercise types.** At minimum: construction (sentence building), transformation (conjugation), completion (particle/blank fill), interpretation (meaning), listening (audio-first comprehension), speaking (spoken response), and conversation (scripted multi-turn scenario). Deterministic validation for constrained tasks; multiple accepted answers per exercise; feedback explains the specific error, never bare correct/incorrect.
- **R4 — Speech.** STT interprets spoken responses; TTS produces prompts and conversational NPC lines. Transcription success is never reported as pronunciation proof — every spoken response shows its transcription for confirmation before grading ("here's what I heard — correct?"). Denying re-records the turn and mints no evidence; after two consecutive denies the turn offers a typed-romaji fallback (production evidence without pronunciation) or a no-evidence advance, so a consistently mis-transcribed utterance cannot deadlock progress. confirming makes that transcription the graded text; STT errors the learner catches at confirmation are therefore not scored against them (the displayed transcript is that chance — a learner who misses a subtle particle error accepts the graded text). No-speech detection uses an independent energy/silence gate rather than Whisper confidence alone (Whisper can produce fluent, confident text from silence). The grader evaluates semantic/grammatical content, not pronunciation. Speech services sit behind a small stable interface (`transcribe(audio, language) → text + confidence`, `synthesize(text, language, voice) → audio`); low confidence or no-speech marks the transcription ambiguous so the app can run the "here's what I heard" verification path. Either model can be replaced without touching the curriculum engine.
- **R5 — Learner profile.** One persistent profile recording, per concept: provenance (previously known / inferred / guessed / explicitly learned), evidence events for recognition, comprehension, explicit explanation, production, generalization, confidence, and retention; plus an error log used to schedule weak-concept review. Familiar-sounding expressions get a faster path (diagnostic → production check), never a free pass to "mastered".
- **R6 — Honest mastery gates.** "Mastered" requires demonstrated production + generalization + at least one delayed retention check (48–72 h+) in a different context. Pre-knowledge diagnostics gate basic content: skipping requires two production demonstrations on different stimuli (a repeat of the same sentence does not count), enforced in code and unit-tested; the gate assesses compositional production, not pronunciation, which the system never scores.
- **R7 — Spaced review.** Taught items resurface on a simple spaced schedule (SM-2-style intervals); reviews are normal session steps.
- **R8 — Vertical slice.** MVP demonstrates one complete loop: ≥1 structured lesson, hands-on written exercises, a listening exercise, a spoken exercise, and a constrained dynamic conversation — all working end-to-end with local speech services.

### Speech acceptance criteria (from handoff §8A, verbatim intent)

1. Both services run locally in Docker on NixOS; 2. no paid speech APIs or API keys; 3. Whisper uses GPU (Vulkan) acceleration; 4. Kokoro produces understandable Japanese on CPU; 5. app transcribes a spoken Japanese response; 6. app synthesizes Japanese prompts and conversational replies; 7. both services stay loaded concurrently within 16 GB system RAM; 8. short spoken interactions feel responsive; 9. transcription failures and ambiguity are handled without misleading feedback; 10. speech services are replaceable independently of the curriculum engine.

Measure in Phase 0: STT latency/accuracy on learner speech, TTS latency and time-to-first-audio, CPU/GPU utilization, peak/idle RAM, VRAM, intelligibility. No invented performance targets — get baselines first.

### Non-goals (explicit deferrals)

Gamification, analytics dashboards, adaptive-learning platform machinery, pronunciation scoring, streaming STT/TTS, music-based features, manga/anime expression import, handwriting, mobile/web clients, multi-user support, general platformization.

## Scope / non-scope

**In scope:** TUI application, declarative curriculum for the planned units, SQLite profile store, spaced-review scheduler, speech HTTP clients + mock, Docker Compose speech stack, integrated DeepSeek evaluator (direct API call, ungraded-save fallback), the Phase 0 machine validation, and the Phase 1 vertical-slice content (one particle/basic-sentence unit, one numbers-and-prices listening unit, one restaurant-ordering conversation).

**Out of scope now:** LLM conversation partner (Phase 2), Ollama local models (only if zero-API-cost becomes a goal), media import, morphological parsing/auto-furigana, pronunciation feedback, any curriculum beyond the listed units.

## Decisions and invariants

### Architecture (module boundaries)

Single Go module at the repo root (recommendation D2), monorepo layout:

```
jplings/
  content/          # declarative units/lessons/steps (YAML), authored with readings
  infra/            # docker-compose.yml + model setup for whisper.cpp & kokoro
  go.mod
  main.go           # TUI entry point (Bubble Tea)
  internal/
    content/        # load + validate content against schema (yaml.v3)
    session/        # session runner state machine (steps, progress, resume)
    exercise/       # exercise kinds and rendering
    grade/          # deterministic graders (multiple accepted answers, error-specific feedback)
    profile/        # SQLite store (modernc.org/sqlite): concepts, evidence events, error log
    schedule/       # SM-2-style intervals; review queue
    speech/         # SpeechClient interface; whisper/kokoro HTTP clients; mock impl
    audio/          # mic recording (pw-record), playback (mpv subprocess)
    convo/          # scripted conversation interpreter (turns, variation, hints)
    tui/            # Bubble Tea views
    eval/           # LLM evaluator interface (DeepSeek API); Phase 1 per S1.7 (rubric grading only)
```

Data flow: `tui → session → exercise/convo → grade → profile/schedule`, with `speech/audio` as leaf services behind Go interfaces. Content files are read-only to the engine; the engine owns no pedagogy.

Deployment: the TUI app runs on the host (terminal + microphone + speakers); Whisper and Kokoro run in Docker Compose containers per handoff §8A, reachable only on internal HTTP endpoints.

### Decisions

- **D1 — Interface: TUI (Bubble Tea), not web or pure CLI.** Rustlings-style but with screens; conversation and listening exercises need interactive display plus audio without a browser stack. Bubble Tea + Bubbles + Lip Gloss is the most complete TUI component set available and pairs naturally with Go (D2). Single user, single machine — web adds a server and browser for zero reach. *Confirmed by Alan 2026-10-31.*
- **D2 — Implementation language: Go.** Same single static binary on NixOS as Rust, with none of the async-runtime or borrow-checker friction; goroutines fit the TUI + HTTP + audio event flow; yaml.v3 schemas validated at load give the same content safety as serde with a little explicit code. Rust's only extra advantages here — compile-time exhaustive matching and zero-cost abstractions — are marginal for a single-user content-driven TUI, and the Rustlings heritage is aesthetic, not technical (recorded so the debate is not reopened). Rejected alternatives: Rust (only for heritage preference), Python (runtime/packaging friction on NixOS for a TUI), TypeScript/ink (no static-binary simplicity, weaker audio story). *Confirmed by Alan 2026-10-31.*
- **D3 — Grading: deterministic backbone + integrated LLM evaluation via DeepSeek API.** Deterministic graders cover all constrained exercises; one `internal/eval` interface adds a DeepSeek HTTP client called directly from the app — no separate service, no agent loop, no Ollama, no extra infrastructure. It grades open-ended responses with separate meaning/grammar/naturalness/register rubrics in a single structured call (pinned model id, temperature, and JSON response schema; the returned object is schema-validated). Any failure — unavailable API, non-200, unparseable body, or schema mismatch — is handled identically: the response is recorded ungraded and surfaced as "could not grade — saved for review" (never auto-passed, never a crash), and session state resumes cleanly per R1. AI-graded feedback is clearly labeled. The slice includes one spoken free-form production exercise (STT transcription graded through it); Alan independently grades a 10-response sample drawn from the slice's real attempts accumulated across sessions (Unit A's graded exercise is the source; ≥10 distinct attempts must accumulate before the audit runs), including cases where a valid off-target form appears (飲めない-class); agreement is scored per rubric dimension (meaning, grammar, naturalness, register — same verdict per dimension on each response). The rubric covers meaning, naturalness, and register only — grammar is graded by the deterministic grader, which already owns the valid_off_target logic, so the LLM is not asked to reproduce it. Each subjective dimension has an authored rubric with anchored examples before the audit runs. Alan independently grades a 10-response sample drawn from real attempts accumulated across sessions (Unit A's graded exercise; if fewer than 10 exist by Phase 1 close, the sample is topped up with curated seed responses including a 飲めない-class case), and agreement is scored per dimension (same verdict per dimension on each response). Passing requires ≥9/10 per dimension, expanding to ≥27/30 if a dimension falls short. This is a smoke gate measuring agreement, not proof of correctness — the soft dimensions carry agreement-only evidence, which is recorded in the work log and must not on its own justify wider LLM-grading rollout in Phase 2. Disagreements drive prompt fixes and re-audit, capped at two re-audit cycles; if a dimension still fails, only that dimension's evidence is withdrawn for the exercise (grades stay visible, labeled lower-confidence) — the exercise keeps running and never loses its whole evidence path. If fewer than 10 real attempts exist by Phase 1 close, curated seed responses top up the sample so learner volume cannot stall the gate. The pending-grading queue retries on the next session and, after two failed retries, flags the response for Alan's manual review; ungraded responses are never counted as mastery evidence, online or offline. The rubric treats unintended-but-legitimate forms (e.g., 飲めない) as valid, not errors. The DeepSeek API key comes from an environment variable (never committed; .gitignore excludes local secrets); if it is absent the app warns at startup that open-ended exercises queue ungraded rather than degrading silently. Spoken transcriptions are sent to DeepSeek's API for grading — an intentional, learner-consented exception to the local-first speech stack. The scripted conversation (D4) stays deterministic in the MVP; Phase 2 may add an LLM conversation partner behind the same interface, constrained to the learner's known grammar/vocabulary budget. Ollama local models remain off the table unless zero-API-cost operation becomes a goal (RAM budget + 8B-class Japanese grading quality uncertain).
- **D4 — Conversations are scripted scenarios with bounded variation, not open-ended chatbots.** Each scenario: turns, per-turn accepted response classes (patterns + wildcards), hints on mismatch, a small branch/novelty budget (different items, days, prices). Predictable, testable, honest; matches "constrained by current knowledge while allowing natural variation." Phase 2 may optionally add an LLM conversation partner behind the same scenario interface, with the system prompt constrained to the learner's known grammar/vocabulary budget.
- **D5 — Profile store: SQLite (modernc.org/sqlite, pure Go), not JSON files.** Progress must survive crashes mid-session (data-loss rule); transactions give that for free. A checkpoint backup of the database file is written on clean exit and on the first launch of each calendar day when the last backup is over 24 h old, keeping the latest 7 snapshots, so six months of mastery evidence cannot be lost to one corrupted file (no wall-clock scheduler is required). Rejected: append-only JSON (corruption risk, harder error-history queries).
- **D6 — Scheduling: in-app SM-2-style intervals.** Rejected: FSRS (better long-term but extra integration cost now; revisit if retention data shows SM-2 inadequate) and any Anki bridge (adds a second tool for the learner to run). The scheduler takes an injectable clock so retention gates are testable without wall-clock waits. SM-2 schedules ordinary reviews; a separate 48–72 h retention queue schedules one different-context check when a concept first clears production + generalization — passing it is the R6 retention evidence.
- **D7 — Content format: YAML per unit/lesson; typed exercise enum; authored readings.** Every Japanese string carries its kana reading plus an authored romaji form (the D11 modality ladder's romaji rung is authored content, not mechanical romanization); no morphological parser in MVP (Sudachi is the Phase 3 option if auto-furigana is ever needed). Content validation = schema lint + answer-set sanity as a build check. Written answers are typed as romaji by default (matching the learner's demonstrated output). Matching runs two passes but only one earns credit: the **exact** pass normalizes spelling conventions only (Hepburn/wāpuro: si/shi, tu/tsu, hu/fu, zi/ji, jya/ja) and is the sole path to a correct verdict. A second **close** pass (vowel length and gemination collapsed) never awards credit — Japanese vowel length is phonemic, so おばさん is a different word from おばあさん — it mints no evidence, re-asks the item later in the session, and reports the distinction by name ("はせん → はっせん", "おばさん is aunt; おばあさん is grandmother"). Typed answers are therefore spelling-strict while spoken answers stay pronunciation-lenient (S1.6), and neither path conflates the two. Content may add per-exercise accepted variants; a grader test matrix covers these cases, kana/kanji answers are accepted when typed via an IME, and prompts always display kana and kanji+furigana — no romanization is generated.
- **D8 — Speech integration: `SpeechClient` interface, HTTP clients, mock for tests.** App never imports whisper/kokoro internals; compose stack exactly as handoff §8A (Vulkan GPU STT, CPU ONNX TTS, persistent models, TTS caching/pre-generation of lesson audio). Container ports bind to 127.0.0.1 only, with a local bind assertion in the compose smoke check.
- **D9 — Curriculum spine: Tae Kim grammar order + sentence-first vocabulary.** Tae Kim's guide is free, CC BY-NC-SA 3.0 (verified 2026-10-31 via guidetojapanese.org and the Creative Commons wiki; acceptable for personal use; any derived redistribution must honor BY-NC-SA). Vocabulary taught in i+1 sentences (Tango-style), authored in-house for slice content; JMdict (CC-BY-SA) and Tatoeba (CC-BY) supply dictionary data and example sentences later with attribution. Initial units target the learner's demonstrated weaknesses: particles は/が/を, です/だ politeness, verb-class identification and conjugation, te-form, questions, もう/まだ, numbers→counters/prices/time, indirect pragmatics (ちょっと…かな, 行こうか).
- **D10 — Personalization is evidence-based, not preference-based.** Per-unit pre-check (recognition → comprehension → production); familiar items get a condensed lesson plus a production check; errors feed the weak-concept review queue; retention checks reuse the concept in a new context; Cantonese/shared-character bridges appear only where they genuinely aid understanding (電/気/星/夜 pattern), never forced.
- **D11 — Modality ladder per concept: romaji → kana → kanji+furigana; listening exercises are audio-first** (no written prompt on first pass; text revealed after the attempt).
- **D12 — Commits and experiments.** No implementation commits before approval; no experiments on main. The 2026-10-31 "Initialize repository" commit is setup only.

## Implementation

Ordered phases; independent slices within a phase may run in parallel.

Budget: Phase 0 — 2 weeks; Phase 1 — 6 weeks; Phase 2 — 8 weeks; consolidation and review buffer — 8 weeks (≥2 weeks of which is reserved before the trip and never consumed by new units). **Trip gate:** if Phase 0 + Phase 1 exceed 8 weeks combined, re-scope Phase 2 to trip-critical grammar only (verb classes/conjugation, te-form, questions, もう/まだ, requests and clarification, and indirect pragmatics such as ちょっと…かな refusals and 行こうか suggestions), deferring lower-value units; the gate is checked at Phase 1 midpoint (week 4), at Phase 1 close, at the midpoint of Phase 2, and monthly — the 8-week Phase 0+1 ceiling therefore has a midpoint alarm rather than being discovered only when it has already been hit; mid-Phase-2 slippage triggers re-scoping rather than silently eating the buffer. ### Phase 1 — MVP vertical slice (the small app)

- **S1.1 Scaffold.** Nix flake devShell (Go), `go.mod` skeleton, content YAML schema + lint. *Checks:* `go test ./...`, `go run . lint content/`.
- **S1.2 Core engine.** Session runner state machine; exercise kinds; deterministic graders with multiple accepted answers, error-specific feedback, and intended-meaning-vs-grammar separation (Round 3 lesson). Transformation graders carry an explicit valid_off_target set (e.g., 飲めない for "negative of 飲む") returning "valid Japanese, different meaning" plus an explanation instead of an error. *Checks:* unit tests for all seven R3 kinds (construction, transformation, completion, interpretation, listening, speaking, conversation) incl. wrong answers, alternate valid answers, off-target-but-valid forms, exact-vs-lenient romaji matching, malformed input.
- **S1.3 Profile + scheduler.** SQLite store, evidence events, SM-2 intervals, review queue. *Checks:* persistence across restart; mastery-gate test (familiar item without production, generalization, and retention evidence cannot be mastered — honest gating is enforced by the engine); skip-gate test (a familiar item with one production demonstration, or two demonstrations of the same stimulus, cannot be skipped); retention-queue scheduling per D6; database backup/restore test.
- **S1.4 Speech client + audio.** `SpeechClient` interface, HTTP clients, mock; recording via `pw-record` (PipeWire) with push-to-talk endpointing (keypress start/stop) plus an energy/silence gate for no-speech detection (VAD model deferred; the gate is explicitly silence-only, the confirmation screen states plainly that the transcript will be graded, so background audio transcribed into plausible Japanese is visible before it counts), mpv playback with defined TTS-down degradation: retry once, then reveal the written prompt (audio-labeled unavailable) and let the session continue cleanly. *Checks:* contract tests vs mock (ambiguous/low-confidence, silent recording → no-speech, noise recording → flagged for confirmation, universal transcription confirmation confirm and deny paths, two consecutive denies → typed-romaji fallback and no-evidence advance with no evidence minted); live smoke test vs real containers (acceptance criteria 5–6, 9–10).
- **S1.5 TUI.** Navigation, lesson/exercise/conversation screens, audio interaction. *Checks:* manual walkthrough + smoke test.
- **S1.6 Slice content.** Unit A: basic sentences & particles は/が/を (with pre-check diagnostic), including one spoken free-form production exercise (STT, DeepSeek-graded); Unit B: numbers → prices/counters listening (diagnostic-gated per the 38,750 finding), including one spoken number/prices response exercise (STT, deterministic grader); Conversation C: restaurant ordering (をください, questions, bounded variation). All with readings, accepted answers, explanations. Every spoken response — including conversation turns and deterministic spoken-number answers — passes through the same confirm/deny step before matching or grading. Conversation matching normalizes kanji to kana using the authored readings (no morphological parser); the homophone→kana table is bounded to scenario vocabulary, kana-only transcription is validated during S0.1 (and dropped from the plan if whisper.cpp lacks it), and a correct-but-unlisted polite variant (お水をください where 水をください is authored) must matched rather than false-mismatch, and kana-only transcription is requested from whisper.cpp where supported. A tolerated variant is reported as such, with a hint naming the omitted particle, so dropping を in みずください still teaches rather than silently passing; tolerated hinted turns mint no correct or production evidence. Counter normalization covers digit-versus-kana spellings only and never strips a counter the prompt requires — omitting 円 yields missing-counter feedback; rendaku and irregular readings (ろっぴゃく, はっぴゃく, さんぜん, ひとつ/ふつか, ひとり) are authored as accepted answers with grader tests. The spoken-number grader likewise normalizes digits, kanji numerals (三千五百円) and kana spellings but keeps required counters, and a gemination-only difference (はせん vs はっせん) is a pronunciation note rather than a scored miss — consistent with R6's rule that pronunciation is never scored. Unit B's pre-knowledge diagnostic likewise targets compositional production, not pronunciation.
- **S1.7 LLM evaluator + spoken open-ended exercise.** `internal/eval`: DeepSeek HTTP client (key from environment variable, never committed), single rubric prompt (meaning/grammar/naturalness/register), ungraded-save fallback per D3, labeled AI feedback. Unit A's spoken free-form production exercise is graded through it. *Checks:* unit tests with a mock HTTP round-trip (API-down, non-200, malformed JSON, and schema-mismatch responses all → ungraded-save → pending-grading queue); live call against the fixed sample; Alan's independent per-dimension grading (meaning, naturalness, register) must meet the D3 audit threshold.
- **S1.8 Vertical slice integration.** The R8 loop on the real speech stack. *Checks:* one broad end-to-end run covering success and failure paths (silent recording → no-speech, ambiguous transcription, confident-but-wrong transcription still confirmed before grading, garbage input, TTS unavailable → text-reveal degradation, DeepSeek API down → ungraded-save); with the injectable clock, the run asserts the mastery gate blocks without production, generalization, or retention evidence — it cannot complete a real 48–72 h retention cycle. A separate wall-clock check — owned by Alan, acceptance: the gate clears and records retention evidence — exercises the D6 retention queue (48–72 h later, different context) and is recorded in the work log.

## Risks and open questions

- **RK1 — NixOS/RDNA4 Vulkan whisper compatibility** is the least-validated infrastructure assumption. Mitigation: S0.1 runs first; fallback is whisper.cpp CPU (slower but correct) with explicit learner sign-off relaxing speech criterion 3 (GPU preferred, not mandatory) — the app is insulated by `SpeechClient`.
- **RK2 — Kokoro Japanese naturalness** unverified. Fallback: Piper Japanese voice or pre-recorded clips for lesson audio.
- **RK3 — LLM evaluation reliability/cost.** Mitigation: deterministic backbone with ungraded-save fallback when the API is down (no mastery evidence is minted), rubrics, labeled AI feedback, sampled manual audits; DeepSeek usage at this scale is pennies.
- **RK4 — Content authoring effort.** Mitigation: reuse Tae Kim/Tango-style ordering, JMdict/Tatoeba data, author one unit at a time, LLM-assisted drafts with human review (LLM never sole correctness authority).
- **RK5 — Learner consistency/motivation is the dominant project risk.** Mitigation: short-session path (one or two steps fit in a few minutes), instant startup, honest progress, review integrated into the normal loop.
- **RK6 — Overestimating mastery from familiar expressions.** Mitigation: engine-enforced gates (req R6, D10).
- **RK7 — Scope creep.** Mitigation: defer list above is the contract; new wants go to Phase 3 or a decision log entry.

Blocking questions resolved 2026-10-31: Q1 Go + Bubble Tea confirmed; Q2 DeepSeek API integrated directly in the app (no agent loop, no Ollama, no separate service); Q3 slice content confirmed.

Disposition of handoff §9 Q9 (authentic human speech in listening exercises): MVP listening audio is Kokoro TTS with the pre-recorded-clip fallback (RK2), but a small authentic-human-speech set is pulled into the Phase 1/2 listening path so the top-priority skill is not trained only on synthetic prosody (this is also the material for S0.2's unfamiliar-speech baseline). Audio licensing differs from Tatoeba text (CC BY 2.0 FR): audio licences are per-contributor, so only clips whose contributor licence explicitly permits reuse (CC BY or CC0) are used, each with recorded attribution; audio with no licence is never reused outside Tatoeba.

Non-blocking (decidable later): **Q5** how sessions end (wrap at natural step boundary vs hard stop); **Q6** whether the Phase 2 conversation partner is worth adding at all (scripted scenarios may suffice).
