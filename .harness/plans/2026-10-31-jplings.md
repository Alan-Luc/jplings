# jplings — Personalized Japanese Learning System

Status: ready
Updated: 2026-10-31

## Goal and context

Turn one learner's fragmented, exposure-derived Japanese into coherent, retained, independently usable everyday conversational ability before a trip in ~April 2027 (≈6 months). Rustlings' loop is the model: **Learn → Exercise → Feedback → Demonstrate → Progress → Revisit later**, with an emphasis on doing over recognizing.

The learner is a beginner in practical proficiency with strong receptive intuition: reads hiragana, some katakana/kanji; understands familiar spoken expressions; can assemble basic but particle/conjugation-inconsistent sentences; has compositional number knowledge (diagnosed correct structure at 38,750); weak on godan/ichidan conjugation, tense/te-form production, particle functions, もう/まだ distinctions, and indirect pragmatic meaning. Speaking and listening are the top priorities; reading (manga, signs) matters; handwriting is out of scope.

The speech infrastructure direction is already decided by prior research (handoff §8A) and is not re-opened: Whisper via whisper.cpp with Vulkan GPU on the RX 9060 XT, Kokoro 82M via ONNX Runtime on CPU, independent Docker containers on the NixOS host. Remaining speech work is validation and benchmarking on the real machine, not technology selection.

Source of record for learner requirements: `docs/references/handoff.md` (the full project handoff, verbatim).

## Requirements and acceptance

This section is the concise product requirements document.

### Functional

- **R1 — Core learning loop.** A session is a sequence of small steps (learn, practice, listen, speak, converse, review). Sessions of 10–60 minutes advance the curriculum without breaking progression; state persists and resumes cleanly mid-unit.
- **R2 — Declarative content.** Curriculum content (units, lessons, exercises, rubrics, explanations, accepted answers) lives in data files, separate from the execution engine. Adding or editing a lesson never requires recompiling the engine.
- **R3 — Exercise types.** At minimum: construction (sentence building), transformation (conjugation), completion (particle/blank fill), interpretation (meaning), listening (audio-first comprehension), speaking (spoken response), and conversation (scripted multi-turn scenario). Deterministic validation for constrained tasks; multiple accepted answers per exercise; feedback explains the specific error, never bare correct/incorrect.
- **R4 — Speech.** STT interprets spoken responses; TTS produces prompts and conversational NPC lines. Transcription success is never reported as pronunciation proof — the grader evaluates semantic/grammatical content and says "here's what I heard" when uncertain. Speech services sit behind a small stable interface (`transcribe(audio, language)`, `synthesize(text, language, voice)`) so either model can be replaced without touching the curriculum engine.
- **R5 — Learner profile.** One persistent profile recording, per concept: provenance (previously known / inferred / guessed / explicitly learned), evidence events for recognition, comprehension, explicit explanation, production, generalization, confidence, and retention; plus an error log used to schedule weak-concept review. Familiar-sounding expressions get a faster path (diagnostic → production check), never a free pass to "mastered".
- **R6 — Honest mastery gates.** "Mastered" requires demonstrated production + generalization + at least one delayed retention check (48–72 h+) in a different context. Pre-knowledge diagnostics gate basic content (e.g., skip basic counting if number production is demonstrated).
- **R7 — Spaced review.** Taught items resurface on a simple spaced schedule (SM-2-style intervals); reviews are normal session steps.
- **R8 — Vertical slice.** MVP demonstrates one complete loop: ≥1 structured lesson, hands-on written exercises, a listening exercise, a spoken exercise, and a constrained dynamic conversation — all working end-to-end with local speech services.

### Speech acceptance criteria (from handoff §8A, verbatim intent)

1. Both services run locally in Docker on NixOS; 2. no paid speech APIs or API keys; 3. Whisper uses GPU (Vulkan) acceleration; 4. Kokoro produces understandable Japanese on CPU; 5. app transcribes a spoken Japanese response; 6. app synthesizes Japanese prompts and conversational replies; 7. both services stay loaded concurrently within 16 GB system RAM; 8. short spoken interactions feel responsive; 9. transcription failures and ambiguity are handled without misleading feedback; 10. speech services are replaceable independently of the curriculum engine.

Measure in Phase 0: STT latency/accuracy on learner speech, TTS latency and time-to-first-audio, CPU/GPU utilization, peak/idle RAM, VRAM, intelligibility. No invented performance targets — get baselines first.

### Non-goals (explicit deferrals)

Gamification, analytics dashboards, adaptive-learning platform machinery, pronunciation scoring, streaming STT/TTS, music-based features, manga/anime expression import, handwriting, mobile/web clients, multi-user support, general platformization.

## Scope / non-scope

**In scope:** TUI application, declarative curriculum for the planned units, SQLite profile store, spaced-review scheduler, speech HTTP clients + mock, Docker Compose speech stack, integrated DeepSeek evaluator (direct API call, deterministic fallback), the Phase 0 machine validation, and the Phase 1 vertical-slice content (one particle/basic-sentence unit, one numbers-and-prices listening unit, one restaurant-ordering conversation).

**Out of scope now:** LLM conversation partner (Phase 2), Ollama local models (only if zero-API-cost becomes a goal), media import, morphological parsing/auto-furigana, pronunciation feedback, any curriculum beyond the listed units.

## Decisions and invariants

### Architecture (module boundaries)

Single Go module at the repo root (recommendation D2), monorepo layout:

```
jplings/
  content/          # declarative units/lessons/steps (YAML), authored with readings
  infra/            # docker-compose.yml + model setup for whisper.cpp & kokoro
  go.mod
  main.go           # TUI entry point (Bubble Tea)
  internal/
    content/        # load + validate content against schema (yaml.v3)
    session/        # session runner state machine (steps, progress, resume)
    exercise/       # exercise kinds and rendering
    grade/          # deterministic graders (multiple accepted answers, error-specific feedback)
    profile/        # SQLite store (modernc.org/sqlite): concepts, evidence events, error log
    schedule/       # SM-2-style intervals; review queue
    speech/         # SpeechClient interface; whisper/kokoro HTTP clients; mock impl
    audio/          # mic recording (pw-record), playback (mpv subprocess)
    convo/          # scripted conversation interpreter (turns, variation, hints)
    tui/            # Bubble Tea views
    eval/           # Phase 2 only: LLM evaluator interface (DeepSeek API)
```

Data flow: `tui → session → exercise/convo → grade → profile/schedule`, with `speech/audio` as leaf services behind Go interfaces. Content files are read-only to the engine; the engine owns no pedagogy.

Deployment: the TUI app runs on the host (terminal + microphone + speakers); Whisper and Kokoro run in Docker Compose containers per handoff §8A, reachable only on internal HTTP endpoints.

### Decisions

- **D1 — Interface: TUI (Bubble Tea), not web or pure CLI.** Rustlings-style but with screens; conversation and listening exercises need interactive display plus audio without a browser stack. Bubble Tea + Bubbles + Lip Gloss is the most complete TUI component set available and pairs naturally with Go (D2). Single user, single machine — web adds a server and browser for zero reach. *Pending final confirmation.*
- **D2 — Implementation language: Go.** Same single static binary on NixOS as Rust, with none of the async-runtime or borrow-checker friction; goroutines fit the TUI + HTTP + audio event flow; yaml.v3 schemas validated at load give the same content safety as serde with a little explicit code. Rust's only extra advantages here — compile-time exhaustive matching and zero-cost abstractions — are marginal for a single-user content-driven TUI, and the Rustlings heritage is aesthetic, not technical (recorded so the debate is not reopened). Rejected alternatives: Rust (only for heritage preference), Python (runtime/packaging friction on NixOS for a TUI), TypeScript/ink (no static-binary simplicity, weaker audio story). *Pending final confirmation; this is the one decision that rewrites implementation details.*
- **D3 — Grading: deterministic backbone + integrated LLM evaluation via DeepSeek API.** Deterministic graders cover all constrained exercises; one `internal/eval` interface adds a DeepSeek HTTP client called directly from the app — no separate service, no agent loop, no Ollama, no extra infrastructure. It grades open-ended responses with separate meaning/grammar/naturalness/register rubrics in a single structured call, with a deterministic fallback when the API is unavailable and AI-graded feedback clearly labeled. The slice includes one open-ended production exercise using it; a fixed manual-audit sample validates DeepSeek's Japanese grading early. The scripted conversation (D4) stays deterministic in the MVP; Phase 2 may add an LLM conversation partner behind the same interface, constrained to the learner's known grammar/vocabulary budget. Ollama local models remain off the table unless zero-API-cost operation becomes a goal (RAM budget + 8B-class Japanese grading quality uncertain).
- **D4 — Conversations are scripted scenarios with bounded variation, not open-ended chatbots.** Each scenario: turns, per-turn accepted response classes (patterns + wildcards), hints on mismatch, a small branch/novelty budget (different items, days, prices). Predictable, testable, honest; matches "constrained by current knowledge while allowing natural variation." Phase 2 may optionally add an LLM conversation partner behind the same scenario interface, with the system prompt constrained to the learner's known grammar/vocabulary budget.
- **D5 — Profile store: SQLite (rusqlite, bundled), not JSON files.** Progress must survive crashes mid-session (data-loss rule); transactions give that for free. Rejected: append-only JSON (corruption risk, harder error-history queries).
- **D6 — Scheduling: in-app SM-2-style intervals.** Rejected: FSRS (better long-term but extra integration cost now; revisit if retention data shows SM-2 inadequate) and any Anki bridge (adds a second tool for the learner to run).
- **D7 — Content format: YAML per unit/lesson; typed exercise enum; authored readings.** Every Japanese string carries its reading (furigana inline); no morphological parser in MVP (Sudachi is the Phase 3 option if auto-furigana is ever needed). Content validation = schema lint + answer-set sanity as a build check.
- **D8 — Speech integration: `SpeechClient` interface, HTTP clients, mock for tests.** App never imports whisper/kokoro internals; compose stack exactly as handoff §8A (Vulkan GPU STT, CPU ONNX TTS, persistent models, TTS caching/pre-generation of lesson audio).
- **D9 — Curriculum spine: Tae Kim grammar order + sentence-first vocabulary.** Tae Kim's guide is free, CC BY-NC (acceptable for a personal tool; attribute; do not redistribute commercially). Vocabulary taught in i+1 sentences (Tango-style), authored in-house for slice content; JMdict (CC-BY-SA) and Tatoeba (CC-BY) supply dictionary data and example sentences later with attribution. Initial units target the learner's demonstrated weaknesses: particles は/が/を, です/だ politeness, verb-class identification and conjugation, te-form, questions, もう/まだ, numbers→counters/prices/time, indirect pragmatics (ちょっと…かな, 行こうか).
- **D10 — Personalization is evidence-based, not preference-based.** Per-unit pre-check (recognition → comprehension → production); familiar items get a condensed lesson plus a production check; errors feed the weak-concept review queue; retention checks reuse the concept in a new context; Cantonese/shared-character bridges appear only where they genuinely aid understanding (電/気/星/夜 pattern), never forced.
- **D11 — Modality ladder per concept: romaji → kana → kanji+furigana; listening exercises are audio-first** (no written prompt on first pass; text revealed after the attempt).
- **D12 — Commits and experiments.** No implementation commits before approval; no experiments on main. The 2026-10-31 "Initialize repository" commit is setup only.

## Implementation

Ordered phases; independent slices within a phase may run in parallel.

### Phase 0 — Machine validation and learner baseline (no application code)

- **S0.1 Speech stack bring-up + benchmarks.** On the target NixOS host: Docker Compose with whisper.cpp (Vulkan) and Kokoro ONNX (CPU), per §8A. Benchmarks: Whisper Small vs Medium on unfamiliar and beginner-produced Japanese; STT latency; TTS FP32 vs INT8, thread counts 2/4/6, time-to-first-audio; concurrent RAM/VRAM; intelligibility. *Checks:* the 10 speech acceptance criteria; benchmark table recorded.
- **S0.2 Learner baseline diagnostics.** Listening comprehension (unfamiliar speech), audio-only vs written comprehension, spontaneous spoken responses, 48–72 h retention, transfer to unfamiliar verbs. Informs pacing and explanation style; explicitly not a prerequisite for Phase 1.

### Phase 1 — MVP vertical slice (the small app)

- **S1.1 Scaffold.** Nix flake devShell (Go), `go.mod` skeleton, content YAML schema + lint. *Checks:* `go test ./...`, `go run . lint content/`.
- **S1.2 Core engine.** Session runner state machine; exercise kinds; deterministic graders with multiple accepted answers, error-specific feedback, and intended-meaning-vs-grammar separation (Round 3 lesson). *Checks:* unit tests per exercise kind incl. wrong answers, alternate valid answers, malformed input.
- **S1.3 Profile + scheduler.** SQLite store, evidence events, SM-2 intervals, review queue. *Checks:* persistence across restart; mastery-gate test (familiar item without production + retention evidence cannot be mastered — honest gating is enforced by the engine).
- **S1.4 Speech client + audio.** `SpeechClient` interface, HTTP clients, mock; recording via `pw-record` (PipeWire), mpv playback. *Checks:* contract tests vs mock; live smoke test vs real containers.
- **S1.5 TUI.** Navigation, lesson/exercise/conversation screens, audio interaction. *Checks:* manual walkthrough + smoke test.
- **S1.6 Slice content.** Unit A: basic sentences & particles は/が/を (with pre-check diagnostic); Unit B: numbers → prices/counters listening (diagnostic-gated per the 38,750 finding); Conversation C: restaurant ordering (をください, questions, bounded variation). All with readings, accepted answers, explanations.
- **S1.8 LLM evaluator + open-ended exercise.** `internal/eval`: DeepSeek HTTP client, single rubric prompt (meaning/grammar/naturalness/register), deterministic fallback, labeled AI feedback. Unit A gains one free-form production exercise graded through it. *Checks:* unit tests with a mock HTTP round-trip; live call against a fixed sample; manual audit of 10 graded responses.
- **S1.9 Vertical slice integration.** The full R8 loop on the real speech stack, including a scheduled 48 h+ retention step. *Checks:* one broad end-to-end run covering success and failure paths (silent answer, ambiguous transcription → "here's what I heard", garbage input, DeepSeek API down → deterministic fallback); honest-gating assertion.

### Phase 2 — Curriculum breadth, LLM conversation partner, retention pipeline

Additional units along the Tae Kim spine (verb classes, te/ta/nai/tai forms, volitional, questions and sentence-final particles, time/dates/counters, もう/まだ and aspect, indirect pragmatics, asking for clarification); optional LLM conversation partner behind the Phase 1 eval interface, constrained to the learner's known grammar/vocabulary budget; wider use of LLM grading for open-ended responses with ongoing sample audits; delayed-retention review queue surfaced in every session.

### Phase 3 — Personalization deepening and media import (deferred until usage data exists)

Adaptive diagnostics, confidence calibration, manga/anime expression import → exercise generation, auto-furigana via Sudachi. Explicitly not scheduled yet.

## Risks and open questions

- **R1 — NixOS/RDNA4 Vulkan whisper compatibility** is the least-validated infrastructure assumption. Mitigation: S0.1 runs first; fallback is whisper.cpp CPU (slower but correct) — the app is insulated by `SpeechClient`.
- **R2 — Kokoro Japanese naturalness** unverified. Fallback: Piper Japanese voice or pre-recorded clips for lesson audio.
- **R3 — LLM evaluation reliability/cost.** Mitigation: deterministic backbone with deterministic fallback when the API is down, rubrics, labeled AI feedback, sampled manual audits; DeepSeek usage at this scale is pennies.
- **R4 — Content authoring effort.** Mitigation: reuse Tae Kim/Tango-style ordering, JMdict/Tatoeba data, author one unit at a time, LLM-assisted drafts with human review (LLM never sole correctness authority).
- **R5 — Learner consistency/motivation is the dominant project risk.** Mitigation: 10-minute minimum sessions, instant startup, honest progress, review integrated into the normal loop.
- **R6 — Overestimating mastery from familiar expressions.** Mitigation: engine-enforced gates (R6, D10).
- **R7 — Scope creep.** Mitigation: defer list above is the contract; new wants go to Phase 3 or a decision log entry.

Blocking questions resolved 2026-10-31: Q1 Go + Bubble Tea confirmed; Q2 DeepSeek API integrated directly in the app (no agent loop, no Ollama, no separate service); Q3 slice content confirmed.

Non-blocking (decidable later): **Q5** how sessions end (wrap at natural step boundary vs hard stop); **Q6** whether the Phase 2 conversation partner is worth adding at all (scripted scenarios may suffice).
